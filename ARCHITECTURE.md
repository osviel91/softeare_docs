# Architecture

Architectural notes for **Software Docs Manager**. This document is kept lean
and is updated as the system grows. It records _why_ decisions were made so the
project stays maintainable and evolvable by its owner.

## 1. Core pipeline

The diagram domain flows through explicit, testable layers:

```
Sequence DSL / Event-flow DSL
     │
     ▼
Lexer / Parser          → produces tokens + a ParseResult<SequenceDiagram>
     │                     (AST + diagnostics)
     ▼
Domain AST              → source-annotated, framework-free model
     │
     ▼
Semantic validation     → participants defined? message targets known?
     │
     ▼
Layout Engine           → pure AST → DiagramLayout (geometry, no SVG)
     │
     ▼
Render Model            → what the renderer draws (derived from layout)
     │
     ▼
SVG Renderer            → deterministic SVG string / DOM nodes
```

Each layer is a pure function of its input and has no knowledge of the layers
above or below it. Tests target each layer independently.

Notes take a deliberately separate, much shorter path:

```
Markdown source → markdown renderer → escaped HTML (+ data-diagram-link)
```

The renderer is pure and framework-free (see ADR-010). Resolving a
`[[Diagram]]` link happens in the UI, which is the only layer that knows the
workspace.

The project-intelligence layers sit **beside** that pipeline, never inside it:

```
project resources ─► tab strip (one open-document set) ─► editor + preview
        │
        ├─► search documents ─► project search (pure scan) ─► results + reveal
        ├─► archive manifest ─► deterministic ZIP ─────────► export / import
        └─► MCP tools/resources ─► stdio JSON-RPC ─────────► coding agents
```

A _resource_ is a sequence diagram, event flow, or Markdown document. Locally,
event flows use the `.eventseq` extension and share the persisted diagram
collection with sequence diagrams. `src/domain/workspace/resource.ts` is a thin
view over the concrete stores rather than a second persistence model (ADR-015).
The domain keeps four concerns distinct: resource identity, content, stored
semantic metadata, and derived presentation information. `ResourceMetadata`
currently contains only an optional description and tags; effective titles remain
derived from existing content titles with the current resource-name fallback.
Visualization is not metadata; stored metadata is propagated through server
persistence and the existing resource read/write surfaces.

### Server resource history

The server's `resources.revision` remains the current optimistic-concurrency
token. H13 uses that existing number as the historical sequence, without giving
it semantic-version meaning. `ResourceRevision` is a domain value containing the
complete logical document state: content, resource type, normalized
`ResourceMetadata`, authorship provenance, and `createdAt`. Representation stays
derived from content and type rather than being persisted.

The workspace operation journal inserts the canonical row, revision snapshot,
operation record, and audit row in one PostgreSQL transaction. Content is supplied
to that transaction from the already-staged mutation, so a successful mutation
cannot lack its snapshot. Human, agent, and system/legacy provenance are kept as
distinct JSON shapes; missing legacy actor information is recorded as `system`
rather than guessed.

Migration 0010 adds `resource_revisions` with a `(resource_id, revision)` primary
key and cascading resource foreign key. On server startup, pre-H13 resources are
backfilled from their canonical volume file at their existing revision number.
Thus a resource at revision 37 gets truthful baseline revision 37, while revisions
1 through 36 remain unavailable. A missing canonical file stops backfill instead
of creating a fabricated snapshot. Full snapshots are intentionally used first;
there is no delta compression or event sourcing. Moves create a revision for
compatibility, but path is resource identity/location rather than revisioned
document state. Deletes cascade history; restoration and archival are out of scope.
Local and filesystem-only repositories do not gain fake history.
The searchable document set and the archive are both **derived on demand** —
there is no separate index to keep in sync (ADR-017, ADR-018) — which keeps the
workspace local-first and Git-friendly.

Sequence and event-flow source each have their own parser, validator, layout,
and SVG renderer, while the application selects the language from the resource
type. Markdown follows its separate source-to-HTML path below.

The MCP server (`mcp/`) is another consumer of exactly those layers, reached
over stdio instead of React (ADR-037). It differs in only two ways: its
`WorkspaceRepository` is backed by Node's filesystem (`mcp/node-fs.ts`) rather
than the File System Access API, and its transport is newline-delimited JSON-RPC
instead of a DOM. It imports the language, layout, renderer, indexer, outline,
search and service modules unchanged, which is why an agent's diagram and its
diagnostics are the editor's.

## 2. Hard boundaries (invariant rules)

These are non-negotiable and enforced by design, not by lint:

1. **The renderer never parses text.** It only consumes the layout/render model.
2. **The editor never computes diagram geometry.** It delegates to the layout engine.
3. **The parser does not know React exists.** The language layer has zero UI imports.
4. **Persistence does not depend on UI components.** Repositories are plain TS.
5. **The domain AST does not depend on CodeMirror.** Editor state is mapped into the AST.
6. **File APIs live behind a repository/adapter.** React never touches `window.showDirectoryPicker` directly.
7. **Every DSL feature flows through Grammar → AST → Validation → Layout → Renderer.**
8. **The markdown renderer emits escaped HTML and nothing else.** It never resolves a diagram link itself; the UI resolves `data-diagram-link` targets (and `data-resource-link` project links) against the workspace.
9. **Derived state is derived.** The searchable document set and the project archive are computed from the repositories when asked; nothing caches them across a change to the workspace.
10. **The index is the only source of project facts.** Panels, completion, hover, find-references and the overview read the `ProjectIndex`; none of them re-parses or re-counts anything.
11. **Node identity is computed, not stored.** AST nodes carry source ranges; a node's id is a pure function of its kind and range, so the parser stays untouched and the AST↔layout↔SVG chain agrees by construction (ADR-021).
12. **The MCP server owns no documentation logic.** It reuses the service, index and render layers over a Node filesystem repository and adds only transport, tool schemas, reference text and prompts; a new language or check is available to agents the moment it is available to the app.
13. **Hosts are adapters; the application layer is the application.** `apps/api` and `mcp` may import `src/application`, `src/domain`, `src/language`, `src/layout`, `src/renderer`, `src/workspace`, `src/shared` and — because a host is the composition root that picks a driver and runs migrations — `src/persistence`; they may never import each other or `src/features`. A host builds a `Principal` and a `ProjectWorkspaceProvider`; everything below that boundary is identical for a human in a browser and an agent on the wire (ADR-039).
14. **Identity is decided once, at the edge.** No code below a host ever sees an HTTP header, a cookie, a bearer token or a stdio frame; it sees an `ApplicationContext`. A credential is mapped to a `Principal` before any use case runs, and a use case names the `Permission` it needs rather than inspecting a role (ADR-039).

### Authorization (`src/domain/access`, `src/application/authorization.ts`)

```
request ─► host builds Principal ─► use case
                                      │
                            requirePermission(context, projectId, permission)
                                      │
                        policy: restriction → membership → authorize()
                                      │
                       grant (role)  |  refusal (not_found | forbidden)
```

The vocabulary is in the domain (`permissions.ts`): roles, the role→capability
table, the agent profiles, and the OAuth `docs.*` mapping. The decision is a pure
function (`authorize.ts`). The policy is the application layer's single
enforcement point, and the only thing that reads `project_members`.

A use case therefore contains no role logic at all — it names the capability it
needs. That is what makes "an MCP tool must never bypass authorization" a
property of the code shape rather than a rule someone has to remember.

## 3. Shared foundation (`src/shared`)

- **`result/result.ts`** — a tiny, dependency-free `Result<T, E>` type plus
  `ok`, `err`, `isOk`, `isErr`, `map`, `mapErr`. Expected failures (bad input,
  missing files) are values, not exceptions, so callers decide how to surface
  them. This keeps the editor responsive even while typing invalid DSL.
- **`ids/ids.ts`** — pluggable id factories. The default uses `crypto.randomUUID`
  (falling back to a counter); tests inject a deterministic factory so geometry
  and ids are reproducible.

## 4. Tooling decisions

- **Vite + React 18** for a fast dev loop and minimal runtime.
- **TypeScript `bundler` moduleResolution** with `noEmit` in referenced projects,
  using `tsc -b` for project references (fast incremental type-checks).
- **Vitest + jsdom** for tests. Domain/parser/layout tests avoid the browser; UI
  tests use Testing Library and cover workflows, not implementation details.
- **ESLint 8** (classic `.eslintrc.cjs`) with `@typescript-eslint` and Prettier
  via `eslint-config-prettier`. Lint is intentionally conservative to stay green.
- **Prettier** enforces formatting; `format:check` is part of CI hygiene.

## 5. Persistence

A `WorkspaceRepository` interface sits above three implementations:

```
                        WorkspaceRepository
                               ▲
        ┌──────────────────────┼──────────────────────┐
  IndexedDB Repository   File System Access      Node filesystem
  (in-browser projects)  repository (a folder    repository (`mcp/node-fs.ts`,
                         the user opened)         for the MCP server)
```

The domain never imports any of them. The third exists because the
`FsDirectoryHandle` seam ADR-005 introduced turned out to be the right shape for
a second host: the MCP server gets the same repository behaviour — stable ids,
metadata reconciliation, extension-based kinds — from `node:fs`. A project
import/export format (human-readable JSON) provides fallback for
browsers without the File System Access API.

Two smaller adapters sit beside the workspace repository because their lifetimes
differ from it:

- **`HiddenPathStore`** (`src/workspace/hidden-paths.ts`) remembers paths the user
  removed from the app. It is keyed per opened folder and defaults to in-memory
  when Web Storage is unavailable, which keeps "remove from app" reversible
  without teaching the cacheless filesystem repository to hide anything.
- **`VersionHistoryStore`** (`src/workspace/version-history.ts`, plus an
  IndexedDB implementation) holds each diagram's source timeline. It is
  deliberately separate so history survives closing one folder and opening
  another, and so a disk delete can clear it explicitly.

Both are constructed through small factories that check for IndexedDB up front
and fall back to memory, mirroring `createDefaultRepository`.

### The application layer (`src/application`)

Persistence is reached the same way from every host, through one layer:

```
        web (local mode)            apps/api            apps/mcp
              │                        │                    │
              └────────────► src/application ◄──────────────┘
                                  │
                       ┌──────────┴──────────┐
                    domain                ports
                                  │
                        WorkspaceRepository
                       (IndexedDB / folder / server)
```

- **`context.ts`** carries the caller: a `Principal` (internal user id, how it
  authenticated, its scopes) plus a request id. `localContext()` names the
  browser/stdio case honestly instead of inventing a user.
- **`ports.ts`** defines `ProjectWorkspace` and `ProjectWorkspaceProvider` —
  how an application service reaches a project it has already been authorized
  for. Local mode resolves a project to a directory; server mode will resolve it
  from PostgreSQL plus the project storage volume.
- **`errors.ts`** defines `ApplicationError` and its codes; each transport maps
  them to its own surface (HTTP status for the API, a tool-execution error for
  MCP), so a use case names a failure in domain terms once.
- **`project-service.ts`** (formerly `src/services/`) holds the operations that
  reconcile a project's identity record with its files.
- **`local-workspace-provider.ts`** is the local-first implementation of the
  port, with the host injecting the `FsDirectoryHandle` factory so the
  application layer itself never imports `node:fs`.

`DocumentationWorkspace` (`mcp/workspace.ts`) is the documentation application
service built on that port; it moved behind `DocumentationWorkspace.over(provider)`
so the API and MCP adapters can share it. The permission vocabulary the
authorization work builds on lives in `src/domain/access/permissions.ts`.

### Server persistence (`src/persistence`)

Server mode adds a second, independent storage stack beside the local one. It is
reached through the same ports, so the application layer above it is unchanged:

```
             src/application (ports, use cases, catalog)
                          │
        ┌─────────────────┴─────────────────┐
   local providers                  server providers
   (IndexedDB / folder)      (PostgreSQL + project volume)
                          │
                    persistence/
        SqlClient ─► pg (deploy)  |  PGlite (tests)
        migrations, repositories, ProjectStorage, path boundary
```

- **`sql-client.ts`** is the driver port. Repositories are written in PostgreSQL
  SQL with `$1` placeholders and never import a driver, which is why the same
  repository code runs against the deployed `pg` pool and against PGlite in a
  test with no database server.
- **`migrations/`** holds each schema change as a TypeScript module carrying its
  SQL; `migrate.ts` applies the missing ones in order, each inside one
  transaction with the `schema_migrations` row that records it.
- **`resource-path.ts`** is the filesystem boundary: relative-only, no `.`/`..`
  segments, `/` as the only separator, no control characters, bounded length, and
  a percent-decoded re-check. `fs-project-storage.ts` then resolves every path
  with `realpath` and refuses one whose existing ancestors leave the project, so
  a symlink cannot escape a directory whose _text_ was legal.
- **`project-repository.ts`**, **`user-repository.ts`**,
  **`session-repository.ts`** and **`audit-repository.ts`** own the tables;
  **`server-workspace-repository.ts`** answers the shared `WorkspaceRepository`
  contract (plus revisions) from them, and **`server-workspace-provider.ts`**
  hands that to `DocumentationWorkspace`, which is what makes the browser's
  services, the HTTP API and MCP one implementation.

`apps/api` is the authenticated HTTP host. Its `http/` directory is the whole
transport: a router over a plain request value, one file that imports
`node:http`, and one place that maps `ApplicationError` to a status. Configuration
is read and validated once (`apps/api/config.ts`); nothing below it reads
`process.env`.

### Authentication (`apps/api/auth`)

```
Browser ──GET /auth/login──► 302 to the provider (+ signed login-state cookie)
        ──GET /auth/callback?code&state──►
             verify state cookie
             exchange code + PKCE verifier
             verify ID token (signature, iss, aud, exp, nonce)
             (issuer, subject) ──► users row
             session row + HttpOnly session cookie ──► 303 back to the app
```

- **`oidc.ts`** is the provider client: discovery (cached), JWKS (cached, refetched
  once on an unknown key), the S256 challenge, the code exchange, and the
  verifier. Signatures are checked with `node:crypto`'s Web Crypto, not by hand.
- **`login-state.ts`** signs the per-attempt state, nonce, verifier and return
  path into one short-lived cookie, and narrows `returnTo` to a root-relative
  path so a login cannot be used as an open redirect.
- **`routes.ts`** owns the four routes. A failure redirects with a short code and
  logs the reason against a correlation id — the provider's own message is never
  rendered to the browser.
- Sessions live in `src/persistence/session-repository.ts`; the cookie value is
  `sid_<uuid>.<32 random bytes>` and only its SHA-256 is stored, so a database
  read cannot be replayed as a login.
